# [I-04] V2 pool removal can be griefed via AegisEngine share transfers

_Section severity (from Solodit section header): Informational_  
_Audit firm: CODESPECT_  
_Source report: [2026-02-06-Aegis-DFF.md](https://github.com/solodit/solodit_content/blob/main/reports/CODESPECT/2026-02-06-Aegis-DFF.md)_

---

**Description:**

The `_removePool(...)` function checks whether the vault holds any AegisEngine shares before allowing the removal of a V2 pool:

```solidity
function _removePool(PoolId pid) private returns (uint8 idx) {
    AegisTypes.PoolData storage slot = _poolRegistry.getData(pid);
    if (slot.variant == AegisTypes.HookVariant.V2) {
        (uint256 shareBalance,) = AegisDFFAssetLib.v2ShareInfo(pid, aegisEngine);
        // @audit-issue This check can be griefed by transferring shares TO the vault
        if (shareBalance != 0) revert ActivePositions();
    }
    idx = _poolRegistry.remove(pid);
}
```

The check assumes that the vault will only hold AegisEngine shares as a result of legitimate protocol operations. However, AegisEngine shares are ERC6909 tokens and can be transferred freely. An attacker can block V2 pool removal by directly transferring a non-zero amount of engine shares to the vault. As a result, the vault temporarily holds engine shares, causing `_removePool(...)` to revert with `ActivePositions()`.

**Impact:** An attacker can temporarily deny service to the `removePool()` function for any V2 pool at minimal cost. While the owner can recover by calling `dismantlePositions(...)` to clear the shares, the attack can be repeated indefinitely, resulting in a persistent griefing vector.

**Recommendation:** When removing a pool, consider batching the operation with `dismantlePositions(...)` or otherwise ensuring that externally transferred engine shares cannot block pool removal.
