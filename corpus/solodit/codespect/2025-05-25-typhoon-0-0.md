# [C-01] Encrypted notes can be arbitrarily altered and signatures can be replayed

_Section severity (from Solodit section header): Critical_  
_Audit firm: CODESPECT_  
_Source report: [2025-05-25-Typhoon.md](https://github.com/solodit/solodit_content/blob/main/reports/CODESPECT/2025-05-25-Typhoon.md)_

---

**Files:** [`NoteAccount.cairo`](https://github.com/typhoonmixer/typhoon-contracts/blob/a148cf0c83d28e98b1bd21af301bfd55f9a9c3f7/src/NoteAccount.cairo#L48)

**Description:**

Once the deposit is made, an encrypted note is created inside `NoteAccount.cairo` via an off-chain process—this process then generates a proof based on the information stored in `NoteAccount.cairo`. The encrypted note is added through `addNote(...)`, and notes are updated via `updateNotes(...)`:

```cairo
fn addNote(ref self: ContractState, pubKey: EthAddress, encryptedNote: Span<u256>, msg_hash: u256, r: u256, s: u256, v: u32);

fn updateNotes(ref self: ContractState, pubKey: EthAddress, msg_hash: u256, r: u256, s: u256, v: u32, newNotes: Span<Span<u256>>)
```

The main issue is that the signature can be replayed. There is no mechanism to ensure freshness in the signed data. In general, a nonce should be included to make every signed message unique.

There is also a secondary minor issue in the implementation of these functions: `msg_hash` is passed as an input parameter without enforcing any link to the actual `encryptedNote` or `newNotes`. This means the contract does not verify that the message hash corresponds to the provided data. If the owner modifies these values, they would only risk their own funds—assuming the primary replay issue is resolved.

**Impact:** Arbitrary alteration of encrypted notes and potential theft of funds.

**Recommendation:** Prevent replay attacks by introducing a nonce.

**Status:** Fixed
