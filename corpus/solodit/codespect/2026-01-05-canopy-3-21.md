# [I-22] The time_lock status is not updated when it ready

_Section severity (from Solodit section header): Informational_  
_Audit firm: CODESPECT_  
_Source report: [2026-01-05-Canopy.md](https://github.com/solodit/solodit_content/blob/main/reports/CODESPECT/2026-01-05-Canopy.md)_

---

**Files:** [`approve.rs`](https://github.com/canopyfi/canopy/blob/234cd9ca0ca8348e466548513d72a2aba65e84e4/programs/canopy/src/instructions/time_lock/approve.rs#L141)

**Original severity:** Best Practices

**Description:**

When the number of proposal approvers reaches the threshold, the proposal can be executed early, and `early_execution_approved` is set to true.

```rust
pub fn handler(ctx: Context<ApproveTimeLock>) -> Result<bool> {
    //...
    if threshold_reached {
        // Set ready_at to current time to allow immediate execution
        let current_time = Clock::get()?.unix_timestamp;
        time_lock.ready_at = current_time;
        time_lock.early_execution_approved = true;
        //...
    }
}
```

The `time_lock` account defines a `TimeLockStatus::Ready` state, but when a proposal can be executed early, the `time_lock` account is not set to this state.

**Impact:** `TimeLockStatus::Ready` is defined but not used, which may cause ambiguity when querying the `time_lock` account data on-chain.

**Recommendation:** It is recommended to either remove the `TimeLockStatus::Ready` state or set the `time_lock` account to `TimeLockStatus::Ready` when a proposal reaches the threshold, and account for the `TimeLockStatus::Ready` state in `can_execute(...)`.

**Status:** Fixed
